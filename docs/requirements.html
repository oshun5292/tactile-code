1ゴールと範囲

1.1 何を作るか

決定AIがコードを書く時代には、「コードの書きやすさ」より「使い始めたいと思えるか」が大事になる。そこで、ディレクトリをプロジェクトとして記憶し、見た目を自分の好きな形に作れるボード(自由配置・手書きで囲む・線でつなぐ)に置く。カードをクリックすると、従来どおりのエディタが現れ、コーディングもできる。

現状は、VSCode(CLI)をエディタ兼メモ帳として使っている。置き換えではなく、「毎日開く入口」になることを目指す。判断

1.2 MVPの範囲

範囲内容根拠
作るプロジェクトの登録と記憶、言語の自動検知、ボード(カード・自由配置・手書き)、エディタ(ファイルツリー・タブ・マークダウン・コード閲覧と編集)、色の共有決定MVP=ボード+エディタまで(AIなし)
作らないAI会話、GitHub APIへの接続(PR・CI)、コードレビュー機能(差分・行コメント)、スマホ連携、複数人利用、アイコン選択決定AIは次段階 / 決定レビューはPhase 2(Q1)

1.3 成功の目安

  • 判断自分のPCで、VSCodeを開く代わりに、このアプリを毎日開いて、プロジェクトを選べる。
  • 判断マークダウンのメモ(人生設計など)を、このアプリだけで書ける。
  • 判断コードを開いて、軽い編集ができる(重い作業は、必要ならVSCodeで開き直せる)。

2利用者と利用シーン

決定まずは自分だけ(個人利用)。ログイン・課金・利用規約・サポートは、MVPの要件に含めない。公開したくなったら見直す。

利用者像: データエンジニア。Python(初級〜中級)、SQL(初級)、dbt・Snowflake・AWS(学習中)。用途は、人生設計のメモ、TypeScriptでの開発、Pythonでのデータ分析、Snowflake+dbt。

主なシーン

  1. 朝、アプリを開く。ボードに並んだプロジェクトのカードで、各プロジェクトの言語・最終更新・メモを眺める。
  2. 気になるカードをクリックして、エディタに入る。ファイルを開き、マークダウンやコードを編集して保存する。
  3. Escでボードに戻り、手書きで囲んだり、カードを並べ替えたり、カードを線でつないだりして、頭の中を整理する。
  4. 新しいディレクトリを、フォルダ選択でプロジェクトとして追加する。

5段階計画(MVPのあと)

判断順序は私の提案です。MVPのあと、使いながら見直します。

Phase 1
MVP: ボード+エディタ(上の FR-01〜FR-11, FR-15)
Phase 2
コードレビューとGitHub状態(レビューのPhase 2入りは決定): ローカルgitの差分表示、行コメント、GitHub APIでPR件数・CIの状態を取得
Phase 3
AI会話: プロジェクトごとの会話。AIの窓口(インターフェース)を設け、モデルを差し替え可能に。Vercel AI SDK + OpenAI互換API(Gemini無料キー、Ollama)
Phase 4
開発エージェント: OpenCode(必要ならACP)。アプリ内の確認ボタンで権限を扱い、読み書きは指定フォルダ内に限定
Phase 5
スマホ連携: PC側にサーバーを設けて、スマホから指示。(今は作らず、画面とAI実行部分の分離だけ守る)

6データ要件

決定保存先は、アプリ専用のローカルJSONファイル。Windowsでは、アプリのデータフォルダ(例: %APPDATA%\アプリ名\)に置く。

判断保存するもの(案):

  • projects: id、パス、表示名、説明の上書き、ひと言メモ、ボード上の位置(x, y)と大きさ、追加日
  • edges: カード同士のつなぎ(始点と終点のproject id)
  • strokes: 手書きの線(座標の並び、色、太さ)
  • settings: 画面の状態(ズーム位置など)、最後に開いたプロジェクト
  • 全体に schema_version を持たせ、将来の形式変更に備える

保存しないもの: ファイルの中身(各プロジェクトのフォルダにあるものを直接読み書きし、アプリは複製しない)。言語の内訳、最終更新、gitの状態は、毎回計算して取得する(古くならないよう。重ければキャッシュ)。

判断書き込みは「一時ファイルに書いてから置き換える」方式で、保存途中の破損を防ぐ。

削除済みの概念: 「進捗%」と「レビュー件数の大きな数字」(カードから外したため、MVPのデータモデルには持たない)。

この章の根拠の多くは、サブエージェントによる調査報告(2026-10-20)です。公式ドキュメントの再確認は、実装の開始時に行います。未確認

画面(React + TypeScript)見た目、ボード(React Flow)、エディタの表示、画面の一時状態(Zustand)決定React Flow / 判断Zustand
中核(Rust)ファイルの読み書き、パスの検証(登録フォルダの外に出さない)、言語の検知、gitの情報取得、JSONの保存判断
橋渡しTauriの invoke(依頼と応答)と Channel(順序つきの逐次データ)未確認調査報告。公式確認は実装開始時
AI実行(Phase 3以降)Rust側の窓口(trait)の裏に隠し、実装を差し替え可能にする判断
  • 決定コンポーネント化と、フロント/バックエンドの分離。UI部品は再利用できる単位で作る(例: プロジェクトカード、言語バー、GitHubチップ、ファイルツリー、タブ、マークダウン表示)。
  • 判断画面から、ファイル操作やプロセス起動を直接行わない。必ずRustのcommandを経由する(将来のスマホ連携で、同じ窓口を再利用するため)。
  • 判断型の共有は、まず手書きのTS型で十分。(tauri-specta は調査時点でrc版のため、様子見)未確認
  • 事実見た目の部品(36のHTML)は、HTML/CSSの試作です。Reactのコンポーネントとして作り直す前提で、CSS変数(色・書体)は、そのまま持ち込める設計になっている。(出典: samples/36-gentle-bento.html)
  • 判断コードエディタ部品(Monaco か CodeMirror 6 など)は、未選定。選定には、サイズ、日本語入力(IME)、Tauriでの動作、見た目の調整のしやすさの調査が必要(10)。

8非機能要件

観点要件区分
動作環境Windows 11(開発機: メモリ32GB、SSD 1TB)。macOS/Linuxは対象外決定
起動と応答起動から、ボードが見えるまで2秒以内を目標。クリックでエディタが開くまで0.3秒以内(アニメーションなし)判断目標値の案
大きなフォルダ言語の検知は、画面を止めない(非同期)。結果はキャッシュする。ファイル数が1万を超えるフォルダでも、ボードは表示される判断
安全性ファイル操作は、登録したフォルダの内側に限定する(../ などで外に出られない)。MVPは、外部ネットワークへの通信を行わない判断
データ保護JSONの書き込みは原子的に行う。編集中のファイルは、保存前に閉じると警告する判断
オフラインネットワークなしで、全機能が動く。フォント(Fraunces、Zen Maru Gothic、JetBrains Mono)は、アプリに同梱する(試作はGoogle Fontsから読み込み)判断
使いやすさ文字のコントラストを十分に取る。Esc、Ctrl+S、タブ切り替えなど、キーボード操作に対応判断
配布自分のPCにインストールして使う(インストーラの配布や自動更新は、MVPの対象外)判断

9画面(UI)要件

事実確定した見た目の見本: samples/36-gentle-bento.html(ボード、エディタ、色の共有)。ギャラリー: samples/index.html。

9.1 ボード

  • 左上: 「workspace / パス / N projects / week N」の小さな等幅ラベルと、大きな「Projects.」。右上: 自動検知した言語の凡例チップ。
  • カード: 白い角丸の面。上段に言語(色の点+名前+「自動検知」)と内訳バー。題名=ディレクトリ名、パス・ブランチ、説明、ひと言メモ、最終更新、GitHubチップ。小さな絵(簡易アイコン)。
  • 配置: ベントー風に、大小を混ぜて自由に散らす(カードの大きさは、内容に応じて変えられる)。
  • 手書き: ペンツールバー(ペン・色・戻す・消す)。細い線で、丸囲み・下線・コネクタ。
  • カードに置かないもの: 番号、レビュー件数の大きな数字、進捗バー。

9.2 エディタ

  • 上部: 戻るボタン、ディレクトリ名、パス、言語バー、GitHubチップ、ブランチ、ひと言メモ(ボードのカードと同じ見た目の部品)。
  • 3カラム: 左=ファイルツリー、中=タブ+本文(マークダウンは書く/半分/読む。コードは行番号付き)、右=AI会話の領域(MVPでは空、またはPhase 3の予告)。
  • 色: プロジェクトのメイン言語色を、ヘッダー・タブ・ツリー・見出しに引き継ぐ。

9.3 見本からの変更点(MVP)

  • 右側のAI会話の領域: MVPではAIがないため、「Phase 3で追加」の空き領域にするか、領域自体を畳める形にする(未決)。
  • 見本のダミーデータ(進捗%、PR件数、CIの状態など)のうち、MVPで取得できないものは、表示しない(FR-04)。
