1認証とトークン保管

1-1　認証方法の比較

観点は「手間」「安全性」「権限の範囲」「このアプリ(Tauri・個人利用・公開リポジトリ)への適性」です。

A. fine-grained PAT(推奨・最初の一歩)

手間
GitHub の設定画面でトークンを作り、アプリの設定欄に貼るだけ。アプリ側の実装は最小。期限(最大 366 日、または無期限)ごとに作り直しが必要。
安全性
リポジトリと権限を選んで絞れる。漏れても被害範囲が小さい。
権限の範囲
1 つの所有者(ユーザー or 組織)単位。公開リポジトリの読み取りは常に可能。
適性
個人利用で最適。ただし Checks API が使えない(下記)。

B. OAuth App の Device Flow

手間
GitHub で OAuth App を登録し Device Flow を有効化。アプリ内にコード表示画面とポーリング実装が必要。
安全性
ユーザーがブラウザで承認。クライアントシークレット不要なので、配布物に秘密を埋め込まない。
権限の範囲
スコープ(例 repo)単位で、fine-grained より粗くなりがち。
適性
将来、他人に配るなら有力。個人利用では手間が割に合わない。

C. gh CLI のトークンを流用

手間
最小。gh auth token の出力を Rust から取得するだけ。ユーザーは既に gh を使用済み(要件書で gh CLI による確認の記載あり)。
安全性
アプリが gh と同じ強さのトークンを扱うことになる。範囲を絞れない。
権限の範囲
gh のログイン時の権限そのまま(未確認)。
適性
「試す」には良いが、gh 未インストール環境で動かない。常用の正規手段にはしない。

D. GitHub App(ユーザートークン)

手間
App 登録、リポジトリへのインストール、Device Flow の有効化が必要。最も手順が多い。
安全性
権限が細かく、トークンは 8 時間で失効(更新トークンは 6 か月)する設計。
権限の範囲
App と本人の両方がアクセスできるリポジトリのみ。
適性
個人開発の現段階では過剰。公開配布するなら再検討。

事実(出典つき)

  • 事実GitHub は、可能なら classic より fine-grained トークンを推奨している。fine-grained は選んだリポジトリに限定でき、公開リポジトリは常に読み取り可能。1 トークンは 1 つの所有者のリソースに限られる。
    出典: Managing your personal access tokens
  • 事実同ページに「fine-grained トークンでは現在できないこと」として Checks API の呼び出し、複数組織への同時アクセス、自分がメンバーでない公開リポジトリへの貢献などが挙がっている。classic は権限が広く、1 年未使用で削除される。
    出典: 同上
  • 事実Device Flow は POST https://github.com/login/device/code でコードを得て、ユーザーが https://github.com/login/device に入力し、POST https://github.com/login/oauth/access_token をポーリングして取得する。クライアントシークレット不要。コード有効期限は既定 900 秒、最小ポーリング間隔は 5 秒(速すぎると slow_down)。事前にアプリ設定で Device Flow を有効にする必要がある。
    出典: Authorizing OAuth apps
  • 事実GitHub App のユーザートークンは既定 8 時間で失効、更新トークンは 6 か月。Device Flow 対応・シークレット不要。App と本人の双方がアクセスできる資源のみ。
    出典: Generating a user access token for a GitHub App
  • 事実gh auth token は、指定ホスト(既定ホスト)のアカウントの認証トークンを出力する。
    出典: gh auth token
  • 未確認Checks API(/commits/{ref}/check-runs)のドキュメントは、fine-grained PAT に必要な権限を記載しておらず、classic / OAuth は repo スコープが必要と書くのみ(出典)。公開リポジトリで認証なし・fine-grained PAT で実際に動くかは未検証。
  • 未確認gh auth token が返すトークンの種類・権限・保管場所(ドキュメントに記載なし)。
  • 未確認公開リポジトリの PR 一覧などを認証なしで読めること自体は REST の一般知識として有力だが、今回の調査では endpoint ごとの明記を確認できていない。認証なし時のレート制限は 1 時間 60 回(下記、事実)で、5 カード程度でも足りなくなるため、実用上トークンは必要。

2-2　レート制限・ポーリング・キャッシュ

  • 事実主制限(1 時間あたり): 認証なし 60 回(IP 単位)、PAT や OAuth のユーザートークン 5,000 回(ユーザーの全トークンで共有)。
    出典: Rate limits for the REST API
  • 事実副次制限: 同時リクエスト 100 まで、REST は 1 分あたり 900 ポイント(GET は 1 点、POST/PATCH/PUT/DELETE は 5 点)、コンテンツ作成は約 80 回/分・500 回/時。応答ヘッダー x-ratelimit-remaining、x-ratelimit-reset、一部で retry-after。
    出典: 同上
  • 事実条件付きリクエスト: 応答の etag を if-none-match で送り、304 が返れば、認証済みなら主制限に数えられない。ポーリングするなら固定間隔で、x-poll-interval ヘッダーがあればその秒数以上待つ。リクエストは並列でなく直列に。制限に当たったら retry-after に従う。
    出典: Best practices for using the REST API
  • 事実GraphQL の主制限は 1 時間 5,000 ポイント。コスト = 各接続が first/last 上限まで要求した場合のリクエスト数合計 ÷ 100(最小 1)。接続には first/last(1〜100)必須、1 回のクエリのノード上限は 500,000。
    出典: GraphQL rate limits
  • 事実GitHub はポーリングより webhook を推奨。ただしデスクトップアプリは外部から受信できないため、webhook は現実的でない(この点は 判断)。
項目方針案(判断)
ポーリング間隔の目安ウィンドウが見えている間だけ 60〜120 秒に 1 回。非表示・最小化中は止める。ウィンドウにフォーカスが戻った時に 1 回即時更新。「今すぐ更新」ボタンも置く。
使用量の見積もり10 リポジトリ × 2 リクエスト ÷ 90 秒 = 約 800 回/時。304 は主制限に数えられない(事実)ので、5,000 回/時に対して十分余裕がある計算。
キャッシュRust 側のメモリに、リポジトリごとの最後の応答と ETag を保持。画面表示は常にキャッシュから出し、更新は裏で。永続化は初回は不要(再起動時に取り直す)。
失敗時通信失敗・403・429 は「不明」表示にして、前回値を薄く残す。x-ratelimit-remaining が 0 なら次の reset まで停止。連続エラーは指数的に間隔を延ばす(公式の推奨に沿う)。
未連携フォルダorigin が GitHub でない / トークン未設定のフォルダは通信しない。「未連携・ローカルのみ」(FR-04)の表示を維持。

3コードレビュー機能

3-1　必要な要素

  • 差分の取得: 事実GET /repos/{o}/{r}/pulls/{n}/files が各ファイルの filename、status、additions、deletions、patch(任意項目)を返す。最大 3,000 ファイル、既定 30 件/ページ。また PR 取得で application/vnd.github.diff を指定すると diff 形式で取れる。
    出典: REST: Pull requests
    未確認巨大ファイルで patch が省かれるか(ドキュメントに記載なし)。
  • ローカルの差分(PR になる前の差分): 決定Phase 2 はローカル git の差分表示から始める。Rust 側で git の差分を取り、同じ表示部品で見せる(判断)。GitHub の PR 差分とは取得元が違うだけで、表示は共通化できる。
  • 表示(CodeMirror): 事実@codemirror/merge は、2 つの文書を並べる MergeView と、1 つのエディタに元の文書(original)を渡す unifiedMergeView を提供する。どちらも全文のテキストを渡す方式で、パッチ入力の記載はない。
    出典: github.com/codemirror/merge
  • 未確認同ページに「リポジトリは archived、開発先は code.haverbeke.berlin へ移動」とある。npm パッケージの現行バージョンと保守状況、React 19 での扱いは未確認。
  • 判断差分表示は 2 つの経路が考えられる。(a) MergeView に「変更前の全文」「変更後の全文」を渡す(Rust 側でファイル全文を取得: PR なら GET contents 等で base/head の全文が必要、ローカルなら git show)。(b) patch 文字列を自前で整形して読み取り専用表示。(a) は見た目が既存エディタと揃い、行番号が正確。(b) は通信が少ない。最初のスパイクで (a) を試し、重ければ (b) に切り替える。
  • 行コメントの投稿: 事実POST /repos/{o}/{r}/pulls/{n}/comments。必須は body、commit_id、path。位置は line + side(LEFT=削除、RIGHT=追加/文脈)。複数行は start_line + start_side、ファイル全体は subject_type=file。position は非推奨。古い commit_id を使うと、後続コミットで行が変わった時にコメントが outdated になる。
    出典: REST: Review comments
  • レビューの提出: 事実POST /repos/{o}/{r}/pulls/{n}/reviews。event は APPROVE / REQUEST_CHANGES / COMMENT、空なら PENDING(後で提出)。comments 配列(path、body、line/side など)で複数コメントを一括投稿できる。通知が飛び、短時間の大量作成は副次制限の対象。権限は Pull requests: write。
    出典: REST: Reviews

判断投稿は1 コメントずつ POST するより、下書きをためて 1 回の「レビュー作成(comments 配列つき)」で出すのが、通知・副次制限の面でも、ユーザーの意図(まとめて出す)の面でも自然。

  • 判断認証も trait TokenSource(keyring / gh 流用 / Device Flow)として分け、認証方式の変更が他へ波及しないようにする。
  • 判断安全面: 投稿系は project_id から origin を解決し、登録済みプロジェクトのリポジトリ以外には書き込まない。React が任意の URL を渡せない形にする。「パスの安全」の方針と同じ発想。
  • 未確認HTTP クライアントの選択(reqwest など)と Tauri v2 の権限(capabilities)設定への影響。Rust 側の通信なので WebView の CSP は直接関係しない見込みだが、検証していない。

5段階的な進め方(PR の分け方の案)

現在の進め方(機能ごとのブランチ・小さなコミット・ユーザーがマージ)に沿った案です(判断)。

PR内容確認方法
2-0スパイク(使い捨て): PAT で Checks API / Actions runs / PR 一覧を実際に叩き、どの権限で何が取れるかを確定。@codemirror/merge の導入可否も確認。結果をこの文書の「未確認」へ反映

7ユーザーが決める質問(推奨つき)

おもに ①②④ を決めてもらえれば、2-0 を始められます。

Q1　認証方式は? A. fine-grained PAT(推奨) / B. Device Flow / C. gh 流用 / D. GitHub App
推奨A。理由: 個人利用では最も簡単で、権限も絞れる。窓口(TokenSource)は分けておき、後で B に移れる。
Q2　トークンの保管は? A. Windows 資格情報マネージャー(推奨) / B. 暗号化ファイル / C. 保管しない
推奨A。理由: OS の仕組みに任せられ、設定 JSON にトークンが残らない。
Q3　CI の取得は、どこまで求める? A. Actions のみ(Actions: read) / B. Checks API も使う(権限の制約次第) / C. 当面は PR 件数だけ
推奨A。まず 2-0 のスパイクで、B が fine-grained で動くか確認する。ご自身のリポジトリで、Actions 以外の CI(外部サービス)を使っているものはありますか?
Q4　コードレビューの最初のゴールは? A. ① 読むだけ(推奨) / B. ② まで / C. ③ まで一気に
推奨A。理由: 副作用がなく、差分表示の部品を固めるのが先。
Q5　レビューの対象は? A. ローカル差分のみ(決定済みの出発点) / B. 自分の PR も / C. 他人の PR も
推奨A → B の順。公開リポジトリで他人の PR にコメントする使い方は、現状の個人利用の想定に無いため後回し。
Q6　状態の更新頻度は? A. 60〜120 秒の自動 + フォーカス時 + 手動ボタン(推奨) / B. 手動のみ
推奨A。ETag により 304 は主制限に数えられない(事実)ので、負荷は小さい。
Q7　クレートの追加について keyring、reqwest など Rust の依存追加が複数発生します。pnpm add と同様、追加の都度確認する運用でよいですか?
推奨はい。2-0 / 2-1 の PR で、追加する名前と理由を先に提示します。
